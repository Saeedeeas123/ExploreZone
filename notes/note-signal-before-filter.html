Design note · 2026-09 · computer vision · signal processing

Fix the signal before you filter it

Root causes verified in codeGazeSignal

Symptom

A camera-driven pointer, aimed with the eyes, tracked correctly on one axis and vibrated heavily. The natural instinct — and the instinct the previous author followed — is to reach for the filter. Add smoothing, increase the smoothing, add a second filter.

That instinct was already exhausted: the app had a well-known smoothing filter downstream, tuned and present. It still vibrated. That single observation is what turned the problem from “tuning” into “architecture”.

Root causes — all upstream of the filter

#DefectEffect
1 The vertical centre of the right eye was averaged from both eyes' eyelid landmarks instead of the right eye's own lids A noisy, semantically wrong vertical axis — matching the reported “horizontal kind of works, vertical does not”
2 The normalisation denominator switched between eye height and eye width depending on how open the eyelid was Discontinuous jumps mid-gaze, including during blinks
3 The raw landmark offset was multiplied by roughly ×20 and clamped before any smoothing Camera noise amplified ~20×, then handed to a filter that had to fight an already-destroyed signal
4 No head-pose compensation anywhere Iris-offset gaze is confounded by head micro-motion — an unmodelled input

The conclusion

No filter can recover a signal that was destroyed before it arrived. Adding smoothing to a noisy, semantically wrong, discontinuously normalised input produces a smooth version of the wrong answer.

This is why the project was restarted from a clean pipeline rather than patched: the ordering of the stages was the bug, and patching the last stage cannot fix an ordering problem.

The corrected order

  1. Fix the signal: per-eye landmark sets, one stable normalisation denominator, drop blink and low-confidence frames, average both eyes.
  2. Calibrate per axis with visible targets and a running guard.
  3. Filter with a tuned per-axis smoother — mandatory, but only now, on a signal worth filtering.
  4. Add a velocity deadzone and dwell stabilisation so the pointer does not act on jitter.
  5. Interpolate rendering to the display rate.

Acceptance criteria, stated numerically

The pipeline is not “done” when it builds. It is done when a human tests it against numbers: latency under roughly 150 ms, acquisition under a second, jitter bounded over a second of stable gaze, correct tracking on both axes, no mirroring, and correct behaviour over other apps.

Transferable rule When a system with an existing “fix” still fails, check whether the fix is downstream of the damage. If it is, the fix is not wrong — the pipeline order is.
