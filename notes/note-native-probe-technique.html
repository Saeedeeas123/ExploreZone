Debugging a native engine you are not allowed to run

VerifiedJNIMethod

The situation

A native inference engine inside an Android app was failing. Every normal debugging route was closed:

  • No root and no privileged shell, so the app could not be installed programmatically.
  • The automation build in use had no accessibility taps, so the screen could not be driven.
  • Launching a test process directly aborted (exit code 134) because the binary was treated as an untrusted app.
  • Executing custom binaries from external storage was denied outright — that mount is noexec.

In other words: the failing code was native, and there was no way to observe it on the device.

The technique

Rebuild the same native library for the Linux environment instead of Android, and write a small probe that mirrors the JNI function line by line — same model file, same call sequence, same code path. Then run it in the Linux container, where printing works and nothing needs to be installed or tapped.

The mirror has to be faithful to be worth anything: the probe is only useful because the code path is identical. What changes is the visibility, not the logic.

On this device the library built in about two minutes (single library target, six parallel jobs). One linking detail cost a cycle: the probe must link the OpenMP runtime, otherwise the symbols from the library's parallel sections are undefined and the link fails.

Why this generalises

When you cannot observe the failing platform, move the code to a platform you can observe — as long as you keep the code path identical. The obstacle is usually not the bug; it is the lack of a print statement.

What it produced

This approach is how two real defects in an on-device LLM path were isolated and explained (prompt formatting producing an immediate end-of-turn, and conversation state never being cleared). Neither would have been visible from the app side, because the app reported success both times.

Honest limits A Linux probe proves the logic of the code path, not the behaviour of the Android integration layer. If the bug lives in the JNI boundary itself — threading, memory ownership, or the loading of the library — this technique will not find it, and you still need a way onto the device.
