Engineering finding · 2026-10 · on-device ML · measured bytes

MediaPipe model bundles never start with “PK”

MeasuredMediaPipeModel files

The assumption

A .task bundle is a ZIP archive, and every ZIP archive starts with the four bytes 50 4b 03 04 — “PK”. So a file-format guard that checks for PK at offset zero looks obviously correct.

It is wrong, and it rejects every genuine bundle.

Measured offsets

FileFirst bytesZIP header offset
gesture_recognizer.task00 00 50 4b 03 042
A community Qwen2.5-0.5B .task00 00 00 00 50 4b 03 044
A .litertlm bundleASCII magic LITERTLMnot a bare ZIP

So the correct guard is not “does the file start with PK” but “does a ZIP header appear at a small, plausible offset” — and even that is only a sanity check, because the third format above is not a ZIP at all and is perfectly valid.

Why this is worth writing down

The bug is invisible in code review. The guard reads as defensive and sensible; it fails only against real files. I found it by dumping the first bytes of genuine bundles instead of trusting the format spec.

Second finding: what the API actually exposes

Reading the compiled option surface of the inference API (rather than its documentation) showed the knobs that exist — model path, token limits, top-K, LoRA ranks, vision and audio options, backend preference — and confirmed the absence of one knob that would have been the obvious workaround for a caching problem: there is no cache-directory option.

This is a small thing that changes planning: if a capability is not in the compiled surface, no amount of configuration will produce it, and the workaround has to live somewhere else.

Honest limits The crash that motivated this investigation was never evidenced — the app exited with no crash file, no tombstone and no kill record, so the cause of that crash is unknown, not “the header check”. What is verified is the file-format fact and the API surface. The feature was removed rather than chased further, because a failure with no evidence is not debuggable.
