Tasks are not goals: the FIND/DO layer model

Design in progressAgentsAndroid

What failed first

The first version of an on-device agent treated a spoken instruction as a goal and tried to execute it. Two failures came out of real device testing, and both were structural rather than accidental:

  • No termination semantics. After the agent opened another app, returning to the agent re-ran the task and opened it again — a loop that only a force-close could break.
  • Wrong candidate. “Open Telegram and open the first chat” opened a different app entirely. The system had choices and no way to justify or correct them.

The verdict from testing was blunt and correct: the idea was present, the execution model was not.

The model

A task is not a goal. It is an ordered list of layers, and every layer is a pair:

HalfMeaningExamples
FINDLocate the right target at this levelpackage · activity · class · object · element · chat · text field
DOApply exactly one operator to itopen · read · write · append · copy · move · compare

“Open Telegram, then open the first chat” is therefore two layers, each with its own find-and-do, applied recursively: find the Telegram package and open it; then find the chat element and open it.

Why this shape

  • Every step becomes checkable. A single ambiguous decision is isolated in one layer instead of being buried in one big plan.
  • Confidence has a place to live. A scoring layer ranks the candidate options for both halves of every layer, in sub-millisecond time, so the decision is explicit rather than implicit.
  • The language model keeps only the hard work. Long or ambiguous orders, and text analysis or creation, go to the model; everything mechanical stays in code.
  • Termination is representable. A task is finished when the layer list is exhausted — which is exactly the property the first version lacked.

The two rules that make it debuggable

Trace is first-class. Every layer records the candidate options it was presented with, their scores, and the final decision for both the find and the do. If the agent picks wrong, the reason is visible rather than inferred.

Step-confirm. The task can walk layer by layer with a human confirming or overriding each choice — and the confirmations are kept as training data, so the manual step is an investment rather than a cost.

Status of this claim This is a design, not a verified result. It was specified after a rejected build and is currently being implemented. I am publishing it as a design note precisely because the notebook policy is to mark the difference between “measured” and “reasoned” — and this one is reasoned.
