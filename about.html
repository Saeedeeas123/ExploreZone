How I work

Root cause, not symptom

A fix that only removes the visible error is a hypothesis, not a fix. I keep going until the failure is explained — and I reproduce the original failure afterwards to prove it is gone.

Verify on the real device

Unit tests and successful builds are not evidence that something works. Every project on this site has been installed and exercised on an actual phone, by a human, before it was called working.

Measure, then claim

Numbers on this site come from test runs and build logs — perplexity against a baseline, gradient checks, byte sizes, flagged-line counts. If a number is missing, the claim is missing.

Label uncertainty

Measured, inferred, and reported-by-someone-else are three different things. I mark which one a statement is, and I keep unverified material marked as a draft rather than publishing it as a finding.

Stop what cannot be evidenced

When a failure leaves no crash record, no tombstone and no log, further chasing is guesswork. I stop, remove the feature, verify the removal byte-level, and document what was learned instead.

Write it down

Knowledge that lives only in a chat history is lost. Findings get written into reusable procedures and versioned documents, so the next attempt starts where the last one ended.

Environment

The unusual part of my setup is that there is no workstation. Compilation, containers, version control and testing all happen on the same phone I use as the test device:

LayerWhat it is
HostRedmi Note 13 Pro 5G · Android 16 · MediaTek Dimensity 7200 Ultra · 8 cores
Build environmentLinux container (proot Ubuntu 24.04, ARM64) with JDK 17, Android SDK, Gradle/AGP, Python 3.12, git
CIGitHub Actions on forks, patched where the upstream workflow cannot run as shipped
Test deviceThe same phone — no emulator, no second machine

This constraint is deliberate. It forces every dependency, download and toolchain assumption to be explicit, and it is the reason several entries in the notebook exist at all.

What I do not claim

Honest limits
  • I am not a security auditor or penetration tester — ExploreZone's scope explicitly excludes it.
  • Nothing here has been published in a peer-reviewed venue. My "notebook" is a working record, not a paper.
  • Several projects are mid-flight: EyePoint and Cosmo are awaiting device-test rounds, and I say so on the Work page rather than labelling them finished.
  • Anima's face is measured-correct but low-poly; its ears handle isolated words, not continuous speech; its brain is a language model, not a chatbot.
  • The work is currently solo. There is no team size to report and no client logo wall.
  • Where a number came from a vendor rather than my own measurement, the entry says so.
